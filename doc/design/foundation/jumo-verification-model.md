# jumo 可检规约（Machine-Checkable Spec）需求

把 jumo 模型从「结构描述 + 玩具 verify」升级为**机器可检的规约**：让「设计说它怎么工作」这件事第一次**能被机器反驳**。

> 一句话立场：形式化要证明的是**「实现符合已写下的规约」**，证明不了「需求本身对不对」。
> 所以本需求的目标不是"证明系统正确"，而是**把隐式规约显式化**，并对**并发 / 幂等 / 凭据**这些"错了很贵"的地方上模型检查。

## 1. 目的与结论

- 让模型里的每条**不变量**都能被 CLI/CI 机检，失败时给出**反例与定位**。
- 让模型成为**唯一规约源**，并从中**生成**验证工件（属性测试骨架 / 契约测试 / 状态机骨架），而不是靠人再写一遍。
- 把已经存在的四个命令（`jumo verify`、`jumo-code impl-check`、`jumo-code align`、`jumo readiness`）拧成**可强制执行的闸门**。

**非目标（明说不做，防止镀金）**：

- 不做全系统演绎证明（Coq/Isabelle 级）；不做 UI、WPL/OML 内容层、策展数据的证明。
- 不追求"证明后无 bug"——规约本身也会错；本需求的产出是**反例**，不是奖状。
- 不为外部件（`warp-parse` 引擎）做证明，只验**接口契约**。

## 2. 现状：jumo 已有什么、缺什么

| 命令 | 现在能做的 | 缺口 |
|---|---|---|
| `jumo verify` | 校验 flow 的控制流完整性（`next`/`goto`/`match`/`stop`/`exit`）、执行 `verify` 块的给定/期望 | `verify` 是**场景断言**（照抄字面量），不是**不变量**；跑得过 ≠ 语义对 |
| `jumo-code impl-check` | usecase → 代码入口的追踪（`impl/usecases.json`） | 只覆盖"有没有接线"，不覆盖行为 |
| `jumo-code align` | 模型 ↔ Rust/TS 注解一致性 | **有 9 处既有注解漂移**（`--check` 恒失败），所以**当不了闸门** |
| `jumo readiness` | 词典别名、部分就绪度检查 | 未纳入 CI 门禁 |
| 模型本身 | 结构准（struct/variant/command/actor/interface/binding/flow/usecase） | **语义弱**：无全局不变量、无状态机、无跨条目约束 |

**结论**：模型现在是一份"好读的设计文档"，还不是一份"能被机器反驳的规约"。差距就在**语义层**。

## 3. 目标（可验收）

用编号需求表述，每条给出**验收**（对齐仓库"完成定义"习惯）。

### V1 模型不变量语言（可机检谓词）

- 需求：模型里能声明**不变量**（跨条目、可量化），由 CLI 检查（`jumo check` 或 `verify --invariants`）。
- 验收：新增的不变量在违反时以**非零退出 + 定位到条目**失败；在模型上恒真时静默通过。

### V2 结构类不变量（有限图，可穷举）

必须支持并默认启用：

| 不变量 | 说明 |
|---|---|
| 每条 `interface` 的 `entry` 必有 `binding` | 现有的「9 条 binding 缺失」（`agent-work-delivery-plan.md` §1.2，readiness Blocked）应由此一眼可见 |
| 每个 `usecase` 必有 `trigger` + `outcome`（+ 可选 `flow`） | 防止用例悬空 |
| 每个 `variant` 的取值**至少被一处使用**，且无悬空引用 | 顺带消灭"定义了没人用" |
| 跨域引用必须可解析 | 已踩过：`output Discovery.Probe.X` 在 entry 里不解析 |
| 每个 `flow` 可达性：无不可达 step、无悬挂 `next` | 控制流已显式，可直接图检查 |

- 验收：把任意一条现有漂移人工注入后，检查必须失败并指出具体条目；清干净后 `--check` 通过。

### V3 从模型生成验证工件（一次建模，多处验证）

- 需求：从 `binding` 生成**路由鉴权契约测试**（每个管理端点"未带 admin bearer → 401/403"，无遗漏）；从 `flow`/`state` 生成**属性测试骨架**；从协议状态机生成**模型检查骨架**。
- 验收：删除代码里某条端点的鉴权判断后，生成的契约测试失败；`impl-check` 与生成的契约测试**共用同一份** `binding` 源。

### V4 一致性闸门（把工具拧成 CI）

- 需求：`jumo verify` + `jumo-code impl-check` + `jumo-code align --check` + `jumo readiness` **四项全绿**进 CI；任一失败阻断合并。
- 验收：CI 上四项均有独立的 job/步骤与失败信息；`align --check` **漂移归零**后才允许启用该项门禁。

### V5 反例可读

- 需求：任何检查失败，输出必须包含：**哪条不变量 / 哪个条目 / 具体反例值**（例如"这条 entry 无 binding：`AdminViewX`"）。
- 验收：不给模型源码也能从失败信息定位到文件与标识符。

### V6 语义层：状态机与不变量（针对"错了很贵"的三处）

必须支持对下列状态机建模并检查（工具可外挂，不要求写进 jumo 语法）：

| 状态机 | 要证的性质 |
|---|---|
| 凭据 / 注册生命周期（enroll → renew → revoke） | `renew` 后旧凭据**立即失效**（不存在新旧同时可用的窗口）；`revoked` 不可复活；`max_uses` 不被并发绕过 |
| 事实入库（`OBSFACT` → 订阅 → 落库） | 同一 `content_digest` 重放**终态等于单次**；`Accepted/Duplicate/Stale/Rejected` 的 ack **单调**；乱序/重试不破坏 `agent_fact_summary` 覆盖式语义 |
| 工作授权（Standing supersede / pause / resume / revoke） | 任意交错后 agent 拉到的是**最新期望版本**；暂停不丢版本；恢复不复活已终结的工作 |

- 验收：每个状态机有小而精的模型（`TLA+/PlusCal` 或 `Stateright`，或 `Alloy` 做关系模型），能在 CI 上分钟级跑完；**至少能对现有实现给出一个反例**（若实现确实违反），或证明性质在模型假设内成立并写明假设。

### V7 分级采用（明确"哪里投、哪里不投"）

| 子系统 | 值不值得形式化 | 手段 |
|---|---|---|
| 凭据 / 注册生命周期 | 值得（安全、并发、blast radius 大） | 模型检查（V6） |
| 事实入库幂等 / 乱序 | 值得 | 模型检查 + 属性测试 |
| 工作授权收敛 | 值得 | 模型检查 |
| 纯函数（`derive_inventory`、`content_digest`、用途打分、帧分帧） | 值得（成本极低） | `proptest` + `cargo-fuzz` |
| Rust 单函数（入库事务、去重判定、状态迁移） | 值得（按函数挑） | `cargo kani`（有界模型检查）；并发用 `loom` |
| HTTP 路由 / 鉴权绑定 | 值得 | 结构类不变量（V2/V3） |
| WPL/OML 字段映射、UI、策展内容 | **不做** | 只做样例/契约测试 |

- 验收：本表成为"要不要形式化"的默认判据；新提交的形式化工作须引用本表说明归属。

### V8 与外部件（`warp-parse`）的边界

- 需求：对数据面只验**接口契约**（帧分帧、`OBSFACT`/`LOGRAW` 载荷、sink 契约），不试图证明引擎内部。
- 验收：帧分帧有 fuzz 用例；契约 violation 能被测试捕获。

## 4. 分阶段交付

| 阶段 | 交付 | 依赖 | 产出信号 |
|---|---|---|---|
| **P0 闸门基线** | 清掉 `align --check` 的 9 处漂移；把四项工具串成 CI | 无 | `verify + impl-check + align + readiness` 全绿、可阻断合并 |
| **P1 结构不变量** | V1/V2/V5：模型不变量语言 + 结构类穷举 + 可读反例 | P0 | binding 缺失这类问题由检查**直接**指出，而不是只靠 readiness 的间接信号 |
| **P2 生成工件** | V3/V8：路由鉴权契约、属性测试骨架、帧 fuzz | P1 | 模型改一处，生成的测试跟着变 |
| **P3 状态机** | V6：三个状态机的模型检查进 CI | P1 | 凭据/入库/授权各有一个能给出反例的模型 |

**推荐起点 = P0**：它同时是后面一切的地基，且不引入任何新概念，只是把已有工具变成闸门。

## 5. 风险与边界

| 风险 | 说明 | 处置 |
|---|---|---|
| 规约本身写错 | 检查全绿也可能是错的 | 不变量须经评审；反例优先于"通过" |
| 维护成本反噬 | 证明随代码漂移会腐化 | 只对**极小、极稳、极关键**的核心写重证明（V6）；其余用低价手段（属性测试/有界检查） |
| 过度形式化 | 对 UI/内容层投入回报极低 | 以 V7 表为默认判据，越界需说明理由 |
| 与现有工具重叠 | 易造第二套 | 一律扩展 `jumo`/`jumo-code` 子命令，不新起独立工具链 |
