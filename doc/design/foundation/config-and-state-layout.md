# 配置与运行数据：一条不变量与它的推论

> **状态**：**约定**（2026-10-12，v2）。
> **本文怎么用**：这是一条**不变量**（§1）+ 由它推出来的**六条规则**（§2–§7）+ **判定算法**（§9）
> + **机械验收检查**（§10）。加一个新东西时跑 §9；审计一个现场时跑 §10。别把它当清单读。
> **不适用**：纯内存态、日志正文、可丢弃缓存（§11）。
> **实例**：gwlinkd 的落地过程见 [`../edge/gateway-linkd-config-layers.md`](../edge/gateway-linkd-config-layers.md)。
> **做法（recipe）**：从 toml 模板到「声明 `toml` + `.env`」的落地步骤（栈侧 tpl + 运行期加载/回写）见
> [`layered-config-recipe.md`](./layered-config-recipe.md)。

## 1. 不变量

> **I**：*任何持久化数据在被写入之前，它的「可重建性」必须已经确定，并且由**唯一属主**保证。*

拆成两条可检验的子式，后面所有规则都是它们的推论：

- **I.a 唯一属主**：这份数据的写入者只有一个（一个机制、一条代码路径、一处路径）。
- **I.b 可重建性守恒**：
  - **可重建的，不得被当成不可重建**（否则备份与迁移被垃圾污染，真正的现场事实被淹没）；
  - **不可重建的，不得被当成可重建**（否则它会静默丢失，而丢失的代价是不可逆的）。

**为什么是这两条**：系统的失效代价并不连续。可重建的东西丢了是「重来一次」；
不可重建的东西丢了是「换锚 / 换 ID / 重新登记」，而这类动作往往**没有回退路径**
（例：中心没有「重置实例」接口 ⇒ 客户端私钥丢了只能新建实例、换 `gateway_id`）。
所以整套设计的唯一目的，是**让不可逆的东西被识别出来、隔离、并始终被带在身上**；
而「唯一属主」是其前提——只要有第二个写者，可重建的边界就随时可能被悄悄改写。

**推论链**：`I` → 分类（§2）→ 落点（§3）→ 声明（§4）→ 加载（§5）→ 写入（§6）→ 生命周期（§7）。
任何一条规则都可以从 `I` 反推出来；反推不出来的一律不该写进规范。

## 2. 分类：两个维度，不是四种分法（推论 1）

`I.b` 要求先判可重建性；再加上一个**正交**的时效维（活多久），就得到坐标：

| 可重建？ | 时效 | **类** | 判据（一句话） |
|---|---|---|---|
| 是 | 长期 | **R（Reconstructed）** | 删了能由模板/上游/进程重算 |
| 否 | 长期 | **S（Site fact）** | 删了要重新接线、重新做决定 |
| 否 | 一次性 | **O（One-shot）** | 删了**无损**（它的价值在消费那一刻结束） |
| 否 | 长期 | **D（Durable identity）** | 删了要换锚 / 换 ID，**不可逆** |
| 是 | —— | **E（Ephemeral runtime）** | 锁 / 游标 / 实例 ID：进程自己攒的 |

判据的关键在**问题顺序**：先问能不能重建，再问活多久 —— 反过来会把 `O` 误判成 `S`
（一次性券在"能被重建吗"这一问上本就该被判为"不可重建且不必保留"）。

再补一条**正交**属性：**含密性**（是否含私钥 / 口令 / 令牌）。
它**不改变类**，只改变**处置**：含密的 `S`/`D` 归档按**密件**对待（安全且离机存放），
且机密**不落进共享文本配置**（走 `${SEC_*}` → 密钥文件）。

## 3. 落点：分离律（推论 2）

> **R3**：**同一条持久化路径不得同时装 R 与 S/D。**

这不是审美，是机制强制的：栈侧的声明是**路径前缀匹配**，`R` 落 `backup`、`S`/`D` 落 `contract`，
而 `contract ⊥ backup`（父/子目录交叠即**声明错误**）。因此只要 `backup: - configs` 存在，
`configs/**` 下**任何**东西都进不了 `contract` ⇒ 身份与现场态**必须物理挪出**资源树。

```
<组件配置根>/              # R 的家：<comp>.toml（渲染物）
<组件现场根>/              # S 的家：<comp>-pub.env（现场态；永不重渲）
<身份目录>/                # D 的家：证书+私钥**成对**、信任锚、<comp>-pub.env（若栈侧共用）
<运行态目录>/              # E/O 的家：*.lock / upgrade* / regist-token / cache
```

栈侧由此得出**唯二**的两个区（其余都是它们的邻居）：

| 区 | 装什么 | 为什么 |
|---|---|---|
| `identity/` | `S` + `D` | 站点级、dev/prod **共用一份**、含私钥 ⇒ 落在 `contract` 之下 |
| `configs/` | `R` + `E` | 可重渲 / 可删可重建 ⇒ `protect` + `backup`，**永不进 contract** |
| `.wist/` | 机密 | 走 `${SEC_*}`；`protect` + `backup`，不入库不进包 |
| 其余（`dev/`、`packages/`、`data-plane-run/`、`values/`、`sys/`、`.env`） | 各自的邻居 | 见附录 A |

**私钥的落点是硬判据**：只要含私钥或"丢了要换锚/换 ID"，就是 `D` ⇒ 必须在 `identity/` 之下。
反过来，把锁 / 簿记 / 缓存放进 `identity/` 是**把 `E` 冒充成 `D`**，直接违反 `I.b`。

## 4. 声明：档位是函数，不是选择（推论 3）

`I` 要求"可重建性已确定"，那么它必须被**写下来**、且**只能有一种写法**。于是：

```
档位 = f(类, 含密性)
```

| 类 | 档位 | 语义（唯一） |
|---|---|---|
| `R` | 在 `sys/` 里 ⇒ 入库交付；渲染出的实例放 `backup` | 升级**该**覆盖 |
| `S` | `protect`（+ `backup`） | 升级/同步**不覆盖不删除** |
| `D` | **`contract`** ⇒ 自动 `protect` + `backup` + 不进包 | 对外契约：可 `export/import` 独立复原 |
| `O` | 不声明（它不该有稳态） | —— |
| `E` | `ignore` + `protect`（+ 视需要 `backup`） | 不进包、不被覆盖、可删 |

`contract` 的三条语义（**声明即得**，不必重复写进别的档）：**不覆盖 + 必收 + 不进包**。

`f` 的自洽性由三条机械判据守住（`gops prj diagnose`）：

1. `ignore ⊆ protect` —— 不进包的按定义也不该被覆盖；
2. `contract` 与其余档**互不交叠**（含父/子目录）—— 同一路径只写一处；
3. `contract` 路径**必须在场**（缺 ⇒ `contract.missing`）。

> 这三条不是"额外规范"，而是 §3 分离律的**可执行形式**：声明只要自洽，`I` 就不可能被声明层面破坏。

## 5. 加载：拒重是唯一属主的运行时证明（推论 4）

> **R5**：现场态与主配置**分文件加载**，两份合并时**叶子键不许重复**，重复即**拒启**。

"拒启"不是保守策略，而是 `I.a` 的运行时证明：

- 只要进程能起来，就**证明了**没有双写者（不可能"两处都写了、靠加载顺序决定"）；
- 报错必须**可执行**（指明这是升级前的老现场、要删哪几行 / 先手工合值），
  否则 fail-closed 会变成"卡住且不知怎么办"。

配套四条约定（都是"让唯一属主可被寻址"）：

| 约定 | 理由 |
|---|---|
| 主配置路径 = `<COMP>_CONFIG`；现场态路径 = `<COMP>_PUB_CONFIG`（相对按主配置目录解析）；**未设则回落同目录约定名**（存在才用） | 现场态可与主配置**不同目录**（栈侧在 `identity/`），所以路径必须能被显式转达 |
| 现场键给 `#[serde(default)]` | "尚未接线"应落回**业务错误**（“请先接入上级”），而不是 serde 的 `missing field` |
| 系统服务必须给**绝对路径** | systemd/launchd 的 cwd 不确定（`state_dir` / `trust_bundle` 都踩过） |
| `service install --pub-config <path>` 把 env 写进 unit/plist | 否则进程读不到现场态 —— 而失败表现是"未接入上级"，不是崩溃 |

**现场态分两层：声明（`<comp>-pub.toml`）+ 值（同目录 `.env`）** —— 仿 docker-compose：
配置文件里只写 `${VAR}` 引用，`.env` 提供真值。它同时满足两个互相矛盾的要求，
所以**不再需要“哪一层永不重渲”的例外**：

| 层 | 文件 | 内容 | 随版本？ |
|---|---|---|---|
| **声明** | `<comp>-pub.toml`（TOML） | 只有 `${VAR}` 引用；**不含任何现场值** | **随版本走**：可入库、可重渲/覆盖 |
| **值** | 同目录 `.env`（`KEY=VALUE`） | 真值 | **不随版本**：现场唯一写者 |

- **插值**：组件加载声明时把 `${VAR}` 换成真值，来源「**进程环境 > 同目录 `.env`**」，
  支持 `${VAR:-默认值}`；**未定义且无默认值 ⇒ 拒启**（fail-closed，与 `${SEC_*}` 同口径）。
  “忘了写 `.env`”要报错并**指向那个文件**，而不是静默变空、到远处才炸。
- **`.env` 必须在声明同目录**（docker-compose 口径）；要换位置给一个专门的 env 变量（`--env-file` 对应物）。
- 声明是 TOML ⇒ **分段没问题**（`[server]` / `[agent]`）；`.env` 只负责**扁平的值**，两者不再冲突。
  `.env` 的键名由声明里的 `${VAR}` 定（部署方可自定）；值可带可不带引号；`#` 是注释。
- **变量名与配置键解耦**：声明写 `gateway_id = "${GWLINKD_GATEWAY_ID}"` 还是 `"${GATEWAY_ID}"`
  由部署方选；运行的组件**回写值时要读声明里的名字**（不再猜）。

## 6. 写入：属主的种类决定写入方式（推论 5）

`I.a` 说属主唯一；**属主是谁**决定了它被允许怎么写：

| 属主 | 可写的类 | 写入方式（必须的性质） |
|---|---|---|
| 模板渲染 | 只 `R` | 每次覆盖；**幂等**（同输入同输出） |
| 现场脚本 | 只 `S` | **按缺补齐**：「缺」= **键不存在或值为空**（空串是初始态，不是现场选择）；**非空值一律保留**；内容没变不碰 mtime ⇒ **可每次都跑** |
| 运行期进程 | `S`（自己的键）+ `O` | 只写现场态；`O` 在**消费成功后立即销毁** |
| 首次生成 / 上游签发 | 只 `D` | 原子写 + `0600` + **已存在即拒绝覆盖**（损坏报错，绝不静默重置） |

两条推论：

- **主配置里出现 `S`/`O` 就是违约**（那就是第二个写者）——这正是 §5 要拒的重复键。
- **`O` 的属主是"消费方"而不是"持有方"**：把一次性材料长期留在盘上是把它从 `O` 变成
  `S`——违反 `I.b` 的同时制造了一个永久的明文泄漏面。所以 `O` 的正确形态是
  **写 → 用 → 删**，并且 `diagnose` 要能报"已接入却仍残留"。

> **“按缺补齐”的定义要点**：`缺 ≠ 键不存在`，而是 **`键不存在 或 值为空`**。
> 空串是**初始态**（尚未接线），不是一种现场选择 —— 不这么定义会留下一个真实的口子：
> 若在填值之前跑过一次渲染（如手工解包后先 localize），`S` 会被钉成 `""`，
> 之后再填值也**不会**被修正（键已存在）⇒ 进程永远报“未配置”而现场不知所措。
> 实现须区分“变量来的值”（空则补）与“现场自己种的值”（如 `tenant_id`，空也是有效值）。
>
> **但首选是“根本不需要模板”**：`S` 的键是**扁平**的、值又本来自环境变量 —— 直接写成 `.env` 形态，
> 脚本只需“把几个键按缺写进去”，**不需要模板文件、不需要占位符替换、不产生中间渲染物**。
> 只有形状确实需要声明（分段 / 复杂缺省）时才引入模板；那时才面对下面这条方言规则。
>
> **占位符语法 = 替换者语法**（用了模板就不得混用，否则读文件的人会拆错）：
>
> | 占位符 | 谁替换 / 何时 | 值来自 |
> |---|---|---|
> | `{{NAME}}` | `gx.tpl` / **localize 时** | `*.value.json`（渲染值） |
> | `$NAME`、`${NAME}` | 现场脚本 / **init 时** | **环境变量**（gops 注入的合并值） |
>
> **模板只描述长相（若确实需要）：** 现场态文件的**形状**（分段 / 复杂缺省 / 注释）才值得放
> `sys/configs/<comp>/<comp>-pub.toml.tpl`；由**补齐脚本自己**读它、替换 `$NAME`、再按缺合并进现场态。
> **不经 `gx.tpl`、不产生中间渲染物**：该模板的**唯一消费者就是那个脚本**；而现场态**永不重渲**，
> 本来就不能走 `gx.tpl`（那会覆盖现场值）。并对“环境里根本没这个名字”给提醒（拼错护栏）。

## 7. 生命周期：三件事按同一个排序（推论 6）

分类一旦确定，三个动作就是同一排序的不同切片：

| 动作 | 只动 | 一句话 |
|---|---|---|
| 升级 / 重渲 | `R` | **升级动 R**：`S`/`D`/`O` 一律不碰 |
| 备份 / 恢复 | `S` + `D` | **恢复动 S/D**：`backup ∪ contract` |
| 迁移（换机 / 交接） | `D`（+ `S`） | **迁移带 S/D**：只带身份类也能自足 |

由此得到**迁移的定义**：迁移 = *在最少的文件上恢复 `I` 成立*，所以顺序被推出来：
先把 `D` 成对搬到位（含私钥，**先备份**）→ 再把 `S` 从主配置搬进现场态并重渲 `R`
→ 清掉残留的 `O` → 重装服务定义（转达现场态路径）→ 跑 §10。
**新旧混用必然拒启**（§5），这是有意的 fail-closed，好过静默双写。

## 8. 症状不是经验，是推论（反面）

破坏哪条子式，就**必然**出现对应症状。这张表是 §1–§7 的否命题，不是案例集：

| 被破坏的 | 必然症状 |
|---|---|
| `I.a`（两个写者） | 值"有时对有时不对"；靠"两边恰好一致"运行；换域名/手改/非脚本接入后分叉 |
| `I.b`（不可重建当成可重建） | 升级/重渲后现场选择被抹回默认；换机后身份丢失、只能换 ID |
| `I.b`（可重建当成不可重建） | 备份/契约归档里混进锁与簿记；该清理的清理不掉（`protect` 锁死） |
| `O` 无销毁 | 废券/引导 token 明文长期驻留；它同时是泄漏面 |
| 分离律（§3） | 声明报 `contract.overlap`；或者为了绕开它，把该保护的私钥留在资源树里 |
| 加载拒重缺失（§5） | 同一键两处生效、行为由加载顺序决定 |

## 9. 判定算法（加一个新东西时）

输入：你要落盘的一个键 / 一个文件 / 一个目录。执行：

1. **可重建吗？** 否 → 进 2；是 → 进 4。
2. **用一次就废吗？** 是 → **`O`**：运行期写 → 消费即删 → `diagnose` 加"残留"检查。结束。
3. 否则它是 `S` 或 `D`。**含私钥，或丢了要换锚 / 换 ID？**
   - 是 → **`D`**：放身份目录 / 落 `identity/` 之下（成对 + `0600`）；让 `contract` 覆盖它。
   - 否 → **`S`**：放现场态文件（`<comp>-pub.toml`），给"按缺补齐"脚本加一行，给 `serde(default)`。
4. **重渲该覆盖它吗？** 该 → **`R`**：放进主配置模板占位。不该（进程自己攒的）→ **`E`**：运行态目录。
5. 落地后**五处必改**（缺一处就等于没做）：
   ① 模板占位（`R`）/ 补齐脚本（`S`）/ 销毁点（`O`）/ 身份目录（`D`）；
   ② `sys-prj.yml` 对应档位（满足 §4 三条判据）；
   ③ `.gitignore`（含密或运行物要挡 —— `--full` 不读它，所以与声明**两处都要**）；
   ④ 加载侧：`serde(default)` 或必填、路径解析方式；
   ⑤ `diagnose` 一条检查 + §10 一条断言。

## 10. 机械验收检查

**这是"方案"与"流水账"的分界**：下列每条都能一条命令判对错。

```bash
# ① 声明自洽（无交叠 / 无缺失 / ignore ⊆ protect）
gops prj diagnose --strict

# ② 渲染物里不出现现场键（唯一属主的静态检查）
grep -nE '^(control_center_endpoint|gateway_id|trust_bundle)' configs/*/<comp>.toml && echo "违约：现场键出现在主配置"

# ③ 现场态幂等（重渲不覆盖它）
b=$(stat -f %m identity/<comp>/pub.toml); gops sys localize >/dev/null; \
  [ "$b" = "$(stat -f %m identity/<comp>/pub.toml)" ] || echo "违约：现场态被重渲"

# ④ 无残留一次性材料（O 已销毁）
<comp> diagnose | grep -q '已接入但.*残留' && echo "违约：一次性材料未销毁"

# ⑤ 交付包里没有身份（D 不泄漏）
gops sys package --full && tar -tzf <name>-<ver>.tar.gz | grep -qE '^identity/' && echo "违约：私钥进了交付包"

# ⑥ 契约归档自足（D 都在场）
gops prj contract export && tar -tzf <contract>.tar.gz | grep -q 'credential.json' || echo "违约：契约归档缺身份"

# ⑦ 现场态没被“钉死成空”（S 的自愈性）：值为空时，配上 values 再跑一次 localize 应当补上
#    （补不上 = 填值顺序/变量没到位；这是 §6 那个口子的验收）
```

六条全过 = `I` 成立。任何一条不过，都是 §8 里某个症状的前兆。

## 11. 边界（别过度套用）

- **不适用**：进程内内存态、日志正文与轮转分卷、可丢弃缓存、上游可再拉的制品镜像
  （制品属 `R`，但通常走"可重新录入"而非"重渲"，见附录 A 的 `artifacts/`）。
- **判据只看"可重建性 + 含密性"**，不看"它看起来像不像配置"。看起来像配置的运行态
  （`upgrade-cursor.json`）就是 `E`。
- **`contract` 不是"重要文件列表"**：它只装"**不可重建的公开现场事实**"，且其归档是**密件**。
  把日志/缓存塞进去会同时违反 §3 与 §4。
